# Implementation Plan: Core Content Model

**Branch**: `001-core-content-model` | **Date**: 2026-08-16 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/001-core-content-model/spec.md`

## Summary

Build the persistence and domain layer the whole CMS rests on: six entities
(`User`, `Article`, `Page`, `Category`, `Tag`, `Media`), their repositories, the
initial migration, Foundry factories, and tests that prove each invariant is
refused when violated.

The technical approach in one sentence: **rules that belong to a single object go
into that object as intention-revealing methods; rules that need to look at other
rows go into a service; rules that must hold even if the code is bypassed go into
the database as a constraint** — and wherever a rule can be enforced in more than
one of those places, it is enforced in all of them, because the database
constraint is the one that survives a mistake in the layer above.

Concretely:

- Article and Page share their lifecycle through an abstract mapped superclass,
  so status, publication date and the four transition methods are declared once
  and cannot drift apart between two tables.
- Slugs are generated by a pure service (testable without a database), made
  unique by a second service that consults the repository, and backed by a unique
  index. The "frozen after publication" rule lives on the entity, because it needs
  no other row to decide.
- Deletion rules that reshape other rows (uncategorising articles, re-parenting
  child categories, refusing to remove an owner) are services, each paired with a
  foreign-key constraint that makes the forbidden case impossible at the database
  level even if a future caller forgets the service.

No HTTP, no templates, no security configuration, no API resources — those are
separate features that consume this one.

## Technical Context

**Language/Version**: PHP 8.4 (`declare(strict_types=1)` in every file)

**Primary Dependencies**: Symfony 8.1, Doctrine ORM 3.6 + DoctrineBundle 3.3 +
Migrations 4.0, `symfony/string` (`AsciiSlugger`), `symfony/validator`,
`symfony/clock`, `symfony/security-core` (for `UserInterface` only),
Zenstruck Foundry 2.12. **No new Composer dependency is required by this feature.**

**Storage**: PostgreSQL 16, running natively (see
[ADR 3](../../docs/adr/0003-postgresql-natively-instead-of-docker.md)). Schema is
produced by `doctrine:migrations:diff`.

**Testing**: PHPUnit 13 with Foundry factories and `dama/doctrine-test-bundle`
transaction rollback. Unit tests take no container and no database; integration
tests take both.

**Target Platform**: Linux server in CI, Windows 11 for development

**Project Type**: Server-rendered web application with a read-only JSON API — this
feature delivers only its persistence and domain layer

**Performance Goals**: None specific to this feature. The only standing
requirement is that every listing query be indexed on the columns it filters and
orders by, so that listings do not degrade into sequential scans as content
accumulates.

**Constraints**:

- PHPStan runs at **level max** with `checkUninitializedProperties: true`. This
  forbids the usual `private int $id;` on entities — identifiers must be declared
  `private ?int $id = null` and the getter must reflect that.
- Migrations are immutable once committed.
- `composer qa` must pass with nothing relaxed, suppressed or skipped.

**Scale/Scope**: 6 entities, 1 enum, 6 repositories, ~7 services, ~7 domain
exceptions, 6 factories, 5 migrations. Roughly 30 unit tests and 25 integration
tests. No routes, so no functional tests in this feature.

The migration count is five rather than one. This plan first estimated a single
migration; generating `tasks.md` showed that to be incompatible with delivering
the user stories as independently testable increments — US1 cannot be verified
against tables that do not exist yet. Each phase that introduces tables or columns
ends with its own `doctrine:migrations:diff`. Five diff-generated migrations are
how the schema actually evolved, and none is edited after being committed.

| **V. Decisions Are Recorded** | Cross-layer decisions become ADRs | **Pass, with work to do** — two decisions here qualify and are planned as ADR 0005 and ADR 0006. |
| **VI. Status Is Reported Honestly** | `docs/status.md` reflects reality | **Pass** — updated in the same change; the absence of functional tests is stated, not omitted. |

**Judgement call on Principle I**: `User` will implement
`Symfony\Component\Security\Core\User\UserInterface` and
`PasswordAuthenticatedUserInterface`. These come from `symfony/security-core`,
which is not a delivery concern — it has no knowledge of HTTP, sessions or
templates; the HTTP parts live in `symfony/security-http` and
`symfony/security-bundle`, which this feature does not touch. Implementing them
now costs two method bodies and avoids reshaping the entity when sign-in arrives.
Recorded here rather than in Complexity Tracking because it is not a violation.

**Post-Phase 1 re-check**: passed. The design introduced one directory not listed
in `CLAUDE.md` (`src/Exception/`) and one not listed either (`src/Factory/`, which
already has a sibling in `src/Story/`). Both are recorded as documentation tasks
rather than left as silent drift — see Phase 1, "Structure decisions requiring a
documentation update".

**Structure Decision**: single Symfony project, the three-layer arrangement
already fixed by `CLAUDE.md` — `Entity/` holds state and invariants, `Repository/`
holds queries, `Service/` holds rules that span rows. This feature adds no
`Controller/`, `Security/` or `Twig/` code at all, which is what keeps it
independently verifiable: every requirement in the specification can be proven
without starting an HTTP kernel.

Two directories in the tree above are not listed in the `CLAUDE.md` architecture
section — `src/Exception/` and `src/Factory/`. Rather than leave that as drift,
the tasks include updating `CLAUDE.md`. The reasoning for each is in
`research.md`, decisions 10 and 11.

## Complexity Tracking

> Filled only where the design is more elaborate than the obvious alternative and
> that needs justifying. No constitution violations were found, so nothing here
> is an exemption request — these are the three places a reviewer is most likely
> to ask "why not the simpler thing?".

| Choice | Why needed | Simpler alternative rejected because |
|--------|------------|--------------------------------------|
| Abstract mapped superclass shared by `Article` and `Page` | Status, publication date and the four transition methods are one concept with one set of rules; declared twice they will diverge the first time one is fixed and the other is not | Duplicating the lifecycle in both entities was rejected: the specification requires page behaviour to be *identical* to article behaviour (US4 scenario 5), and identity that is maintained by hand is identity that lapses |
| Slug uniqueness split across a pure generator, a collision-resolving service, and a database unique index | The pure part is unit-testable with no database at all, which is where the interesting cases live (accents, punctuation, empty results); the index is what holds under a race two services cannot see | A single service doing everything was rejected because it forces a database into every slug test; relying on the index alone was rejected because a constraint violation is an error, not a resolution — the requirement (FR-011) is to *derive a distinct address*, not to fail |
| Four deletion services in addition to foreign-key rules | Two of the four rules cannot be expressed as constraints at all: re-parenting child categories to their grandparent, and clearing lead-image references in the identity map | Relying on `ON DELETE` alone was rejected: `SET NULL` and `RESTRICT` cover two of the four cases, and a stale in-memory entity after a database-level `SET NULL` is a defect waiting for its first reproduction |
